# Kite 设计宣言

> 牵风，而不是看管数据。

- 状态：长期设计原则
- 适用范围：产品、交互、视觉、架构和验收

## 1. 起点：从柜子到风

Kite 拒绝把文件管理做成沉重的柜子。

传统图形文件管理器继承桌面隐喻。
它把 folder 扩展成柜子、抽屉和仓库。
用户先学习保管。
用户再学习寻找。

folder 的词源指向一层折叠。
它不指向一座仓库。

Kite 不否认数据需要保管。
Kite 否认保管必须是第一体验。

Kite 不试图做一个更整齐的柜子。
Kite 改变用户和文件系统之间的关系。

文件系统持续变化。
目录出现、消失、移动和更新。
版本控制状态持续变化。
设备、网络和本地卷进入同一空间。

用户面对的不是静止库存。
用户面对的是数据流。

因此，Kite 从导航开始。
保管是系统条件。
导航是用户行为。

传统资源管理器体现保管哲学。
Kite 选择导航哲学。

## 2. 核心隐喻：一条可牵引的线

Kite 是线。
传统资源管理器也是线。

传统线的一端连接数据。
它把用户拉向一个固定位置。
Kite 的线连接风。
它让用户感知流向，同时保持控制。

线不是装饰。
线是中介。
线传递意图、阻力、方向和反馈。

用户拉动线。
系统返回位置、状态和结果。
界面负责维持张力。

线失去张力时，导航变成漂移。
线失去自由时，导航变成柜子。

Kite 的设计任务，是让线保持可感知的张力。

## 3. 四个哲学支点

哲学关联不在功能清单。
哲学关联在中介、约束、视角和可逆性。

### 3.1 中介

界面不是容器。
界面是用户意图和文件系统之间的中介。

中介不是无立场通道。
中介选择什么可见、什么可做、什么需要确认。

路径显示位置。
图标显示对象。
状态显示变化。
预览显示内容。
动作结果确认推断。

Kite 的中介必须减少翻译损耗。

设计要求：

- 路径先于装饰。
- 对象状态先于品牌表达。
- 操作反馈先于动画。
- 系统能力先于自造替代品。
- 本地状态和远程状态必须说清。

Windows 使用 GPUI 作为手。
macOS 使用 SwiftUI 和 AppKit 作为手。
两端共享 Rust Core 的数据语义。

同一个哲学不要求同一个渲染器。

### 3.2 约束

风筝没有线，只会被风带走。
约束不是重量。
约束是可控性的条件。

Kite 的约束包括目标、范围、空间和平台能力。

目标是用户操作的对象。
范围是新建、粘贴和搜索发生的目录。
空间决定同时可见的分栏数量。
平台能力决定菜单和系统集成。

约束必须可见。
约束必须可理解。
约束必须可撤销。

设计要求：

- 每个菜单动作携带明确目标。
- 目录级动作携带明确工作目录。
- 行菜单操作行项目。
- 列菜单操作该列目录。
- 窗口宽度决定可见栏数。
- Kite 不设置固定“最多 N 栏”限制。
- 深层栏目通过横向滚动保留。
- 一个层级的加载不改变其他层级的操作语义。

线需要约束。
约束不能变成牢笼。

### 3.3 视角

风没有固定形状。
视角让风显出方向。

分栏视图不是功能装饰。
分栏视图是层级视角。

上级、当前和下级同时在场。
用户看见来源。
用户看见位置。
用户看见下一步。

视角必须稳定。
视角必须随窗口变化。
视角不能依赖隐藏的记忆负担。

设计要求：

- 路径栏持续显示完整位置。
- 分栏保留上级上下文。
- 当前选择不抹掉层级关系。
- 预览服务于当前文件和属性判断。
- 搜索必须显示搜索根目录。
- 滚动必须保留空间方向感。
- 每个分栏目录都能直接打开编辑菜单。

分栏不回答“仓库里有多少层”。
分栏回答“用户现在能看见哪一段路径”。

### 3.4 可逆性

风会改变方向。
线必须允许用户拉回。

可逆性让探索成为安全行为。
不可逆性必须成为明确事件。

设计要求：

- 导航保留返回和前进历史。
- 页签和目录在应用重启后恢复。
- 删除优先进入回收站或废纸篓。
- 长任务支持取消。
- 危险动作要求确认。
- 重命名上级目录后保持有效路径。
- 删除上级目录后回到存在的父目录。
- 操作失败说明对象、原因和下一步。

可逆性不等于隐藏风险。
可逆性表示用户能恢复控制。

## 4. 设计承诺

| 承诺 | 含义 | 验收信号 |
|---|---|---|
| 导航先于保管 | 用户先知道位置，再处理对象 | 路径、层级和历史始终可读 |
| 张力必须可见 | 目标和范围不能依赖猜测 | 动作显示正确对象和目录 |
| 轻不等于空 | 能力存在，但不阻塞当前动作 | 后台任务不冻结界面 |
| 空间表达约束 | 可见层级由窗口决定 | 无固定栏数上限，支持横向滚动 |
| 视角保留上下文 | 上级和当前层级同时可见 | 分栏持续显示路径位置 |
| 可逆优先 | 探索后可以恢复控制 | 历史、废纸篓、会话恢复和确认 |
| 原生是手 | 每端使用正确系统语言 | Windows GPUI，macOS SwiftUI + AppKit |

## 5. 反模式

以下做法违背本宣言：

- 把 folder 当作仓库。
- 把功能数量当作产品重量。
- 让按钮依赖不可见的全局选择。
- 让行菜单和列菜单共享错误目标。
- 在一个层级操作时重载无关层级。
- 用固定层数上限替代空间约束。
- 用重复入口制造能力错觉。
- 用动画掩盖系统延迟。
- 用不可逆动作换取表面速度。
- 为统一界面破坏平台习惯。
- 把空、损坏和加载状态混为一谈。

## 6. 架构映射

### Rust Core

Rust Core 稳定数据语义。
Core 定义路径、对象、命令目标、工作目录、状态和会话。
Core 不依赖 UI 渲染器。

### Windows

Windows 使用 Rust 和 GPUI。
Windows Shell、Recycle Bin 和 WPD 由系统能力承担。
列菜单和行菜单使用明确目标。

### macOS

macOS 使用 SwiftUI 和 AppKit。
Window、Quick Look、Finder、Services 和 Trash 使用原生 API。
macOS 26 使用 Liquid Glass。
macOS 13 到 15 使用标准材质降级。

平台不同。
规则相同。

## 7. 设计评审问题

每次产品、交互或架构变更都回答以下问题：

1. 用户能立即指出当前位置吗？
2. 用户能看出操作对象吗？
3. 用户能看出新建、粘贴或搜索的范围吗？
4. 一个层级的动作只影响目标层级吗？
5. 用户能撤回或返回吗？
6. 加载、空状态、错误和不可用状态清楚吗？
7. UI 在后台工作中保持响应吗？
8. 该平台使用正确的原生中介吗？

任一问题没有明确答案时，设计未完成。

## 8. 宣言

Kite 不把数据放进柜子。<br>
Kite 把数据流变成可牵引的线。

Kite 不要求用户看守文件。<br>
Kite 帮助用户保持方向。

线让风可感。<br>
约束让手可控。<br>
视角让路径可见。<br>
可逆让探索可继续。

Kite 牵的是风。<br>
传统资源管理器牵的是数据。<br>
两者都是线。<br>
差别在于，Kite 用线导航，不用线捆绑。
